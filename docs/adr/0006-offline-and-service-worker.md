# ADR 0006 — Офлайн: свой service worker вместо `vite-plugin-pwa`

**Статус:** Принято, 2026-09-09. Отменяет решение №5 из `docs/research/STACK.md`
(рекомендацию `vite-plugin-pwa`), которое написано до ADR 0001. Закрывает пункт 4
фазы 6 в `PLAN.md`.

---

## Контекст

`PLAN.md` пункт 4 и `STACK.md` §5.2 называют инструмент: `vite-plugin-pwa` 1.3.0,
стратегия `generateSW`, `registerType: 'prompt'`. **Выполнить это буквально нельзя.**
`vite-plugin-pwa` — плагин Vite, а ADR 0001 заменил Vite на Next.js 16 с
`output: 'export'`. Vite в сборке отсутствует; подключать плагин не к чему.
Расхождение чисто хронологическое: §5 писался, когда стек ещё оценивался.

Пересобирать рекомендацию под Next.js оказалось не переводом, а другой задачей —
из-за одного измерения.

### Измерение, которое переворачивает постановку

`STACK.md` §5.1 описывал приложение так: «фиксированный набор хешированных
статических ресурсов плюс один неизменяемый JSON-датасет», и для такой формы
«прекешировать всё — не компромисс, а полное решение». Для Vite-SPA это было верно.
Статический экспорт Next.js устроен иначе. Замеры текущего `out/`:

| Что | Сколько |
|---|---|
| Весь каталог `out/` | **345 МБ** |
| HTML-страниц | 1224, в среднем **200 КБ** каждая, суммарно 239 МБ |
| RSC-пейлоадов (`.txt`) | 4884 файла, остальные ~100 МБ |
| `out/_next` — код приложения целиком | **2,3 МБ** |
| Чанк с датасетом | 742 КБ, **178 КБ в gzip** |

Конфигурация из `STACK.md` §5.2 — `globPatterns: ['**/*.{js,css,html,svg,woff2,json}']`
— на этом дереве попыталась бы прекешировать **345 МБ**. Это не «дороговато», это
неработоспособно: столько не отдадут при установке, не удержат в квоте и вытеснят
при первом же дефиците места.

Причина расхождения в том, что при пререндере каждая из 1224 страниц несёт свой
RSC-пейлоад, то есть данные размножены по страницам. Но **само приложение вместе со
всем датасетом — это 2,3 МБ, и датасет в нём лежит одним чанком**. Отсюда
единственная разумная форма офлайна здесь: кешировать **приложение**, а не страницы.
Один раз загруженная оболочка вместе с чанком датасета умеет отрисовать любую из
1200+ страниц клиентским роутером, ничего не запрашивая.

### Опасность устаревания, которая почти исчезает

`STACK.md` §5.3 верно называет худший сценарий: «вы исправили падеж в датасете,
выложили, а вернувшийся пользователь продолжает видеть неверный ответ, потому что
его service worker отдаёт прекешированный старый JSON. Для обучающего приложения
тихо отдавать устаревшие неверные данные хуже, чем быть офлайн».

Это верно для Vite-SPA, где датасет лежит отдельным `dataset.json` по стабильному
адресу. Здесь — нет: датасет компилируется **внутрь JS-чанка, имя которого содержит
хеш содержимого** (`1w523-3a4wpmh.js`). Новый датасет — новое имя файла. Кеш,
отвечающий по имени файла, не может отдать старый датасет вместо нового: старого
имени в новой оболочке просто никто не спросит.

Остаётся ровно одна устаревающая сущность — HTML-оболочка, которая решает, какие
чанки грузить. Её и надо брать по сети в первую очередь. Тогда самый страшный
сценарий проекта закрывается не дисциплиной, а формой архитектуры.

## Рассмотренные варианты

**`@serwist/next`.** Официальный преемник заброшенного `next-pwa`; собственная
документация Next.js 16 указывает именно на него
(`node_modules/next/dist/docs/01-app/02-guides/progressive-web-apps.md`, «Extending
your PWA», п. 3). Против два довода. Первый: совместимость с `output: 'export'`
**не подтверждена** — в документации `@serwist/next` статический экспорт не
упоминается ни разу, интеграция ставится обёрткой `withSerwist` вокруг
`next.config` и работает на этапе сборки webpack/Turbopack, тогда как экспорт в
`out/` происходит после; манифест прекеша при этом собирается не из того дерева,
которое реально выкладывается. Класс отказов «service worker не создаётся» на
Next 15 в трекерах присутствует. Второй: список прекеша всё равно пришлось бы
задавать вручную — по умолчанию он взял бы те самые 345 МБ. То есть зависимость,
требующая проверки на живом стенде, ради генерации того, что мы всё равно
описываем сами.

**Библиотеки Workbox без плагина.** Дают стратегии кеширования, которых здесь нужно
две, обе тривиальные. Список прекеша по-прежнему собирается руками. Плата — рантайм
в бандл ради двух `if`.

**Свой service worker, без зависимостей — выбран.** Способ регистрации показан в
документации самого Next.js (тот же PWA-гайд, шаг 5): `navigator.serviceWorker
.register(new URL('…', import.meta.url))`, сборщик выносит файл отдельным ресурсом.
Мы полностью владеем списком прекеша — а это ровно та величина, которой в этом
проекте и надо управлять (2,3 МБ вместо 345 МБ). Плата — около восьмидесяти строк
своего кода, включая поток обновления. Для проекта, который написал собственный
инвертированный индекс с Левенштейном, потому что библиотека поиска сочтена лишней,
это ровно тот же порядок работы и тот же способ решать.

**Не делать офлайн вообще, ограничиться установкой на домашний экран.**
`app/manifest.ts` даёт установку без единой зависимости и без единого риска
устаревания. Вариант честный, и его стоило рассмотреть всерьёз: доводы §5.3 писались
против прекеша данных. Отвергнут потому, что установленное приложение, показывающее
динозаврика в метро, хуже неустановленного: установка обещает офлайн, и §5.1 верно
описывает, где справочником по управлению пользуются — в дороге, в аудитории, при
плохой связи. Обещать и не выполнить — худший из трёх исходов.

---

## Решение

**Свой service worker, ноль новых зависимостей.** Плюс `app/manifest.ts` —
встроенная в App Router конвенция, тоже без зависимостей.

### Что кешируется и как

- **Прекеш при установке — только `/_next/static/**` и корневая оболочка.**
  Порядка 2,3 МБ. Датасет входит сюда чанком. 1224 пререндеренные страницы
  **не прекешируются никогда**.
- **`/_next/static/**` — `cache-first`, срок вечный.** Имена содержат хеш
  содержимого, поэтому устаревание структурно невозможно (см. контекст).
- **Навигации и HTML — `network-first` с откатом в кеш.** Сеть есть — пользователь
  получает свежую оболочку; сети нет — отдаётся закешированная, и дальше всё
  рисуется клиентским роутером из чанка с датасетом.
- **Старые кеши удаляются в `activate`** по имени версии.

### Обновление — эквивалент `registerType: 'prompt'`

Новый worker устанавливается и **ждёт**, не перехватывая управление. Приложение
слышит `waiting` и показывает то, что и предполагал `STACK.md` §5.3, — заметное
«новая версия — обновить». Нажатие шлёт `postMessage({ type: 'SKIP_WAITING' })`,
worker вызывает `skipWaiting()`, страница по `controllerchange` перезагружается.
Молчаливого самообновления нет: в приложении, которое учит падежам, подмена
содержимого под руками — не улучшение.

`datasetVersion` из ADR 0005 показывается в панели «о программе»: устаревший клиент
диагностируется одним скриншотом.

### Две ловушки развёртывания

**Заголовки из `next.config` при `output: 'export'` не действуют.** Гайд Next.js
говорит об этом прямо: при статическом экспорте заголовки переезжают на прокси.
Значит `Cache-Control: no-cache, no-store, must-revalidate` для самого `/sw.js`
задаётся **в `_headers` Cloudflare Pages**, а не в конфиге. Без этого браузер может
сутки отдавать старый worker из HTTP-кеша, и поток обновления перестанет работать
именно тогда, когда он нужнее всего. Это продолжение ADR 0004: настройки выкладки
живут вне репозитория, и их надо записывать явно.

**Область действия worker привязана к пути.** ADR 0004 снял `basePath`, потому что
проект едет на поддомен из корня, — и это же условие требуется здесь: worker должен
отдаваться из корня источника. Непустой `NEXT_PUBLIC_BASE_PATH` (переменная в
`next.config.mjs` его допускает) сузит область и тихо отключит офлайн на части
адресов.

### `experimental.useOffline` — не используется

Next.js 16 несёт экспериментальный флаг `experimental.useOffline` и хук
`useOffline` из `next/offline`. Здесь он не нужен и вреден. Он предназначен для
повторов упавших RSC-запросов и Server Actions — в статическом экспорте нет ни того,
ни другого. Его механизм проверки связи — **цикл HEAD-запросов с бэкоффом**, то есть
рантаймовые сетевые вызовы, которых `CLAUDE.md` не допускает («Any runtime network
call whatsoever»). И он бесполезен рядом с выбранным решением: worker и так отдаёт
навигацию офлайн, так что повторять нечего. Индикатор «вы офлайн», если понадобится,
делается штатными событиями `online`/`offline` без флага и без опроса сети.

## Последствия

**Становится легче.** Приложение работает офлайн целиком: весь датасет уже в
кешированном чанке, поиск и справочник не ходят в сеть по построению. Установка на
домашний экран превращает справочник в «вещь на телефоне» (§5.1). Ноль новых
зависимостей.

**Становится труднее.** Восемьдесят строк service worker — свой код со своим
жизненным циклом, а ошибки в нём проявляются на **втором** визите, не на первом
(§5.3, п. 4): любая проверка, сделанная одной загрузкой, ничего не доказывает.
В `ci` этого не поймать, значит проверять руками по чеклисту при каждом изменении
worker.

**Тяжело откатить.** Установленный у пользователя service worker живёт, пока его не
разрегистрируют; выложить «версию без worker» недостаточно — нужна выкладка worker,
который снимает сам себя. Это стоит помнить до первой выкладки, а не после.

**Чего решение сознательно не даёт.** Пререндеренные HTML-страницы офлайн доступны
только те, что уже посещались (через `network-first`-кеш). Холодный вход по прямой
ссылке `/en/warten/` без сети сработает через закешированную оболочку и клиентский
роутер, но первый в жизни визит без сети невозможен — оболочку неоткуда взять.

**Открыто на будущее.** Push-уведомления (гайд Next.js, шаги 2–4) требуют сервера
для рассылки и VAPID-ключей, то есть противоречат «бэкенда нет». Не делаем.
