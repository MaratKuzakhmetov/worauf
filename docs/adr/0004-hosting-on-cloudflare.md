# ADR 0004 — Хостинг на Cloudflare, деплой вне CI

**Статус:** Принято, 2026-09-02. Отменяет решения №10 и №11 из `docs/research/STACK.md`.

---

## Контекст

Отчёт по стеку рекомендовал GitHub Pages плюс деплой из Actions и покупку домена
`worauf.app` или `worauf.eu`. Оба пункта отпали по одной причине: у владельца уже есть
домен и уже есть Cloudflare — там живёт `markgp.com`. Проект поедет на **поддомен**,
а не на отдельный домен.

Это меняет три вещи разом:

- **`basePath` не нужен.** Поддомен обслуживается из корня, поэтому исчезает весь класс
  багов с путями, ради избавления от которого отчёт и предлагал покупать домен.
- **Домен покупать не надо.** Расход, которого нет.
- **Деплой из Actions не нужен.** Cloudflare Pages собирает из репозитория сам; джоба
  с `deploy-pages` была бы вторым конвейером, делающим ту же работу в другое место.

---

## Решение

Хостинг — Cloudflare Pages, на поддомене.

**Деплой запускается тегом `production-*`**, как в `personal-website`: workflow
`deploy.yml` проверяет наличие секрета `CF_DEPLOY_HOOK_URL` и дёргает Cloudflare Deploy
Hook. Именование тегов оттуда же: `production-ГГГГ-ММ-ДД-краткое-описание-NN`.

Публикация по тегу, а не по пушу в ветку, выбрана сознательно: она делает выкладку
отдельным намеренным действием, а не побочным эффектом слияния. Для проекта, который
учит грамматике, «случайно выложил» — не безобидная ситуация.

`ci.yml` вызывается из `deploy.yml` через `workflow_call`, поэтому те же
`lint → typecheck → test → build` проходят **до** обращения к хуку. В `personal-website`
этого шага нет, и тег там выкладывает что угодно; здесь цена ошибки выше.

Джоба `deploy-pages` удалена, вместе с ней ушли права `pages: write` и `id-token: write`
и группа `concurrency`. Файл `public/.nojekyll` удалён — это артефакт GitHub Pages,
на Cloudflare он ничего не значит.

Сборка **остаётся** шагом CI, хотя ничего и не публикует. Причина в ADR 0001: `next dev`
больше не несёт `output: 'export'`, поэтому `npm run build` — единственное место, где
выяснится, что мы использовали возможность, недоступную статическому экспорту.

Адрес сайта приходит из переменной репозитория `SITE_ORIGIN` в `NEXT_PUBLIC_SITE_ORIGIN`.
Если она не задана, сборка подставляет `https://worauf.invalid` — зарезервированный домен,
который не резолвится никогда. Правдоподобно-неверный `canonical` живёт в проде месяцами;
очевидно сломанный замечают в первый день.

## Последствия

**Становится легче.** Один конвейер вместо двух, ноль расходов на домен, ноль путей
с префиксом. В день деплоя меняется одна переменная в настройках репозитория, а не код.

**Становится труднее.** Сборка перестала быть воспроизводимой из одного репозитория:
настройки Cloudflare (команда сборки, каталог вывода `out`, версия Node) живут в его
панели, и в git их нет. Если проект когда-нибудь понадобится поднять с нуля, это придётся
вспоминать. Стоит записать настройки в README, когда деплой будет настроен.

**Ловушка, о которой надо знать.** Deploy Hook просит Cloudflare собрать **ветку,
настроенную в его панели**, а не тот коммит, на который повешен тег. Тег здесь — сигнал
«выкладывай», а не источник кода. Если повесить тег на коммит, который не является головой
продакшн-ветки, Cloudflare всё равно соберёт голову ветки, и выложено будет не то,
что помечено. Практическое правило: тег ставится на голову той ветки, которая настроена
в Cloudflare, и никуда больше.

**Перед первым деплоем** Cloudflare нужно задать: каталог вывода `out`, команду
`npm run build`, Node из `.nvmrc` и переменную `NEXT_PUBLIC_SITE_ORIGIN` со значением
поддомена. В GitHub — секрет `CF_DEPLOY_HOOK_URL` и переменную `SITE_ORIGIN`.
